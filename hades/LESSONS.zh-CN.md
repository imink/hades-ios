# Hades iOS 移植与真机排障经验

## 当前成果与适用范围

截至 2026-10-14，V22 已在 iPhone 15 Pro Max / A17 Pro / iOS 26.7.1
完成开发签名、USB 安装及实际游戏场景运行。用户反馈“成功了”，随后将其确认
为可正常运行的版本。本文把该版本作为本次设备图形问题的可运行基线，
不将它扩展为所有机型、所有关卡或长期稳定性的保证。

两个真机观察窗口分别记录 64/83 个 render pass、467/661 次索引绘制，
零绘制通道均为 0；日志至少记录 3600 次成功呈现。源码、签名包和设备运行
由构建 receipt 关联，覆盖安装前后 10 份存档的路径与 SHA-256 完全一致。
完整 72 项回归通过，最终收尾复跑也通过。

游戏、密钥、解包结果、改写映像、生成着色器、截图、存档、设备日志及签名产物
均不进入仓库。本文只记录工程方法、非敏感统计和可核对的结论；
原始证据保存在本机私有产物目录。

## 1. 参考实现不是另一款游戏的规格

D2R 提供了可借鉴的总体方法：ARM64 原生执行、离线指令改写、
Horizon HLE、线程映射、签名代码页嵌入及图形 API 接管。
不能借用其游戏地址、容量常数、资源格式或触控钩子。

Hades 必须独立核验标题与版本、NSO 构建标识、导入、动态重定位及实际执行路径。
本次建立独立 `hades/` 目标，共享改写器使用显式 `portable-abi` profile，
关闭全部 D2R 专用剪口、观测和地址规则，保留原 D2R profile 的默认行为。

早期曾把 SDK 中的 NVN/EGL 导出看作图形路线线索；实际 main 的 Vulkan 导入
及运行时调用才是决定性证据。Hades 游戏主路线是 Vulkan，经官方 MoltenVK
转为 Metal。早期真实着色器的离屏绑定探针只验证局部能力，不能证明游戏使用 NVN。

**教训：移植架构可以复用，游戏语义必须重新取证；“SDK 有这个接口”不等于游戏在用。**

## 2. 把整个启动链拆成有证据的关口

实际推进顺序为：

1. 本机合法解包，核验标题、版本、ExeFS/RomFS 和模块。
2. 离线 ARM64 ABI 改写、独立结构检查、等价试验及变异负对照。
3. 重定位、受保护映射、原生 EOS/计时调用和 SDK 初始化。
4. 驻留模块构造器、真实 `nnMain`、文件、存档、网络初始化及输入。
5. Vulkan 创建资源、draw/submit/present、音频缓冲回收。
6. Apple 开发签名、真机入口、实际场景和用户目视反馈。

EOS 的提供模块实际位于 RomFS 中的 NRO，不能只搜索常驻 NSO 就断言导入缺失。
NRO 规范化、NRR 成员关系和载荷签名核验也有各自边界，不能外推为完整根证书认证。

SDK 初始化必须遵守实际顺序；直接执行后续初始化入口会读到未建立的线程状态。
每次新增必需系统调用，应让真实路径继续前进，而不是跳过初始化。

**教训：解包成功、进入入口、成功 present 和正确游戏画面，是不同里程碑。**

## 3. 原生 ARM64 兼容的难点是 ABI 和页几何

Switch 与 iOS 都是 ARM64，不等于可以直接跳转执行。必须处理 x18、
TLS、SVC、计时指令、栈指针用法及实际出现的间接跳转表。
跳转表识别要检查边界、基址数据流和有符号偏移，不能仅按相似字节替换。

本次五模块验证覆盖 39359 个非门改写站点，每个至少两次有效等价试验，
并用 500 个变异负对照验证检测器确实能发现错误。这不是全程序等价证明，
但比“改写脚本没有报错”更有意义。

Switch 4 KiB 与 Apple 16 KiB 页粒度不同。单纯放宽对齐检查或把页面设为 RWX
会破坏真实权限和别名语义。本次对 main 使用显式 12 KiB load bias，
重生成相对分支和嵌入前缀，使实际 CodeData transfer pool 满足宿主页约束；
其他模块维持原有布局。必要的子页兼容单独建模，不冒充原生 4 KiB 映射。

iOS 通过已签名 Mach-O `__TEXT` 页和公开 `vm_remap` 恢复执行布局，
没有 CPU JIT。链接后的 15 个 AOT 段必须逐段核对字节、布局和权限，
不能只检查 Mach-O 能否生成。

**教训：地址、权限、别名和生命周期是一个整体，不能只修一个报错条件。**

## 4. 必需 HLE 要有真实状态，不能靠成功空桩推进

内存查询必须来自真实预留分区；线程、事件、transfer memory、BSD endpoint、
domain clone、文件句柄及音频队列必须维持所有权和关闭状态。
不同接口即使名称相似，也不能猜参数寄存器或命令号。

曾把 HID 203 误按许可布尔处理，随后 SDK 使用空对象崩溃。核对实际调用和公开 ABI 后，
确认 203 是创建活动振动设备列表，205 才是振动许可查询。错误实现撤销，
虚拟控制器通过真实的零振动执行器能力避免虚构设备。

只读缓存大小返回 0 也不是无害默认值：它使游戏跳过挂载资源。
修复应提供实际使用的小型缓存，而不是只把返回值改成任意非零数。

离线网络采用明确 local-only 状态，不伪造连接成功；原生 socket 初始化仍真实执行。
未支持的必需服务返回明确错误，不能让后续代码带着无效状态继续运行。

**教训：成功返回是契约，不是进度条；错误要尽量出现在契约被违反的第一处。**

## 5. 内存与音频要测实际行为

512/1024 MiB 堆预算下实际游戏出现空分配；2048 MiB 对照跨过该处。
这是宿主策略选择，不是测得的 Switch 硬件预算，也不代表设备物理内存占用。
resident、physical footprint、virtual 和 Metal allocated 存在重叠，不能求和，
也不能据此断言 Jetsam 原因。

音频不仅要“打开服务”，还要复制有效 PCM、提交真实队列、回收完成 tag，
正确处理事件和关闭。实际缓冲循环曾因空 released 队列未清零输出而失败。
修复完整输出契约后，四个缓冲可循环提交与回收。
回调不能随意进入客体 SDK，也不能与 IPC 关闭路径形成锁顺序死锁。

**教训：资源创建是开始，重复使用、失败回滚和销毁才检验实现是否完整。**

## 6. 首次真机崩溃：先核对分配错误，再看崩溃点

V10 游玩数分钟后崩溃，符号及装载基址对齐后定位到 MoltenVK
`mvkUpdateDescriptorSetWithTemplate` 对空 descriptor set 的访问。
此前已有 `VK_ERROR_OUT_OF_POOL_MEMORY`；不能因为内存统计较高就归因于 Jetsam。

实际批次需要 6144/6528 个集合，每集合三个 uniform-buffer 描述符，
但相关原始池只给 8192 个此类描述符。V11 根据实际布局计算需求，
必要时使用真实 backing pool，并保留 `maxSets`、设备/分配器归属及
free/reset/destroy 生命周期。没有乘任意放大常数，也没有伪造分配成功。

**教训：驱动里的空指针可能是上游错误未处理的结果；修复资源契约，而不是只挡住崩溃。**

## 7. 缺色和闪动：被否定的假设同样重要

| 假设或实验 | 实际证据 | 结论边界 |
|---|---|---|
| iOS 不支持 BC7 | A17 Pro 能力和格式查询支持相关用途；两端实际纹理格式与 view 映射一致 | 不支持“全面 BC7 不可用”的归因，仍不证明采样正确 |
| argument buffer 绑定有问题 | V13 切换直接资源索引，用户确认无改善 | 此开关不是修复 |
| 每次 submit 后等待可消除闪动 | V14 真实 queue wait 成功，症状仍在 | 全队列串行化不是修复，也不排除提交内部问题 |
| 纹理上传损坏 | V16 两端 279 种 BC7 基层 RGB/alpha 缩略图哈希一致 | 已观察存储一致，不覆盖所有 mip、层、view 和绘制时刻 |
| attachment 丢弃导致缺色 | V17 将相关 `DONT_CARE` 改为 `LOAD`，真机无改善 | 此覆盖不是修复 |
| 图形 tracker 漏记 draw | V18–V20 增加原始 Vulkan 调用及客体标量对照 | 非空批次确实存在未提交 draw 的通道 |

截图或帧末纹理不等于通道结束时的内容。R8 动画、镜头和场景时刻不同，
哈希不一致不必然表示损坏；哈希一致也不证明 descriptor 或 shader 采样正确。

诊断表曾溢出，必须先显式记录并解决覆盖不足，不能用被截断的证据断言没有问题。
原始调用也要有界记录，并确认未触及调用上限。

**教训：每次只改变一个关键变量，记录否定结果；不要反复包装已被真机否定的“修复”。**

## 8. 最终有效链：目录顺序 → 布局编号 → 容量 → 绘制拒绝

V21 增加四个受限观测字段：descriptor index、descriptor capacity、
vertex stride、vertex layout。两端同着色器的前三项一致，布局编号不同：
主场景在 iOS 为 layout 2，在 Mac 为 layout 0，步长均为 56 字节。

实际客体按布局注册编号分配缓冲并查询固定容量表。layout 2 只有 200000 字节，
顶点计数停在 3571：`3571 × 56 = 199976`，只余 24 字节，
不足以加入一个新顶点。较晚真机窗口有 25/77 个零绘制通道。

继续沿初始化链追踪，发现布局按首次出现的效果格式追加注册，
而效果加载列表来自目录枚举。宿主直接转发 `readdir` 顺序，
不同文件系统的枚举顺序改变了布局编号及对应容量。

V22 在过滤后、分页读取前，对只读资源目录快照按 `strcmp` 字节序排序：

1. 不修改存档目录顺序。
2. 不重写客体容量表或强塞 Mac 布局编号。
3. 不只放宽检查，否则可能超过真实分配的缓冲。
4. 保留显式开关、严格配置验证和同版本观测，用于验证因果链。

真机主场景随后使用 layout 0 的实际 4 MB 缓冲，步长仍为 56。
较晚窗口计数达到 4641，超过旧阈值；两个窗口零绘制通道均为 0，
并取得用户成功反馈。场景不同，不能把两次 draw 总量当逐帧性能对比。

原始 Horizon 目录枚举契约仍未核实，因此保留 `DirectoryOrderProbe` 命名，
不声称已经证明 Switch 总是按字节序枚举。已证实的是这项兼容策略在当前设备、
当前构建和已观察场景下解除容量瓶颈，并得到用户的画面成功确认。

**教训：看似 GPU 的问题可能来自 CPU 初始化中的不确定顺序。
纹理本身正确，也可能因为 CPU 拒绝 draw 而只留下轮廓或闪动。**

## 9. Mac、Simulator 与真机各自能证明什么

Mac 原生链适合快速验证装载、HLE、输入、资源及机制对照，
但使用不同 GPU 和驱动；不能外推为 iOS 图形修复。
Simulator 也不能替代 A17 Pro 真机验证，现有 iPhoneOS AOT 包不能直接当模拟器包运行。

自进程 GPU 读回只观察本应用，不抓桌面或其他应用；需要的截图权限不可绕过。
用户目视确认是可见画面的证据，运行日志是执行机制的证据，两者互补。

诊断复制、屏障、GPU 等待和日志会扰动时序。因此既保留完整捕获窗口，
也观察不插入通道读回等待的后续窗口；仍不能声称观测完全无扰动。

**教训：快速平台用于缩小范围，目标设备用于确认结果。**

## 10. 测试不能只检查“没有报错”

新增回归围绕实际契约组织，包含 O0/O2、真实 GPU 上传/读回、
分配失败、生命周期、输入参数和负对照。目录回归检查开关、
字节序、单条分页、过滤、文件类型/大小、无遗漏/无重复及 EOF。

Mac 默认文件系统通常大小写不敏感，合成测试不能依赖同时创建
`A.shader` 和 `a.shader`；本次使用不冲突的名字验证排序。

72 项测试通过不等于验证整款游戏；成功呈现计数也不等于正确像素。
必须把测试对象、输入、阈值、输出形状和未覆盖范围写清楚。

**教训：验证所需语义，不用一个方便测量的代理指标替代目标。**

## 11. 真机交付也是工程的一部分

每次交付先由用户退出游戏并授权安装，确认目标设备有线连接、解锁且游戏未运行。
完整备份存档，同 bundle 覆盖安装，不卸载；安装后逐路径核对 SHA-256，
一致后才启动。不得为“省时间”强杀正在游玩的进程。

签名、嵌入、源码、资源和设备运行都必须闭环：

1. 核对 Apple 签名及 Mach-O 可执行页权限。
2. 核对 15 个 AOT 段、291 份资源和 42 份冻结源码。
3. 设备启动核对 build receipt，而非只看安装命令成功。
4. 追加日志按最新 receipt 切分，避免把旧版数据当新版证据。

V22 安装后不能再悄悄改运行时源码却继续称其为同一个已验证包；
文档更新与运行时代码变更要区分。

**教训：可运行版本必须可识别、可追溯，并且不能以损坏用户存档为代价。**

## 12. 数据、权限和工程隔离

没有合法密钥时应暂停游戏特定解包，不能下载第三方密钥或破解包加密。
获得用户明确提供的本机密钥后，仅从指定位置读取，不输出内容。
原 NSP 不改动，生成结果位于仓库外，构建依赖不默认全局安装。

所有源码修改在独立 worktree 中进行，主 checkout 不修改。
上传前检查实际暂存文件，不仅依赖 `.gitignore`；排除游戏、密钥、存档、
个人签名信息和运行日志。参考上游与发布仓库分开，未经授权不得推送参考上游。

遇到平台权限拒绝必须明确报告，不通过替换凭据、绕过系统防护或改推上游规避。

**教训：本地技术验证、分发权限和远程写权限是三件事。**

## 13. 去黑边不是放大输出窗口

Hades 的宿主 Metal 视图、客体窗口、游戏内部虚拟视域和 UI 是独立层次。
单独放大 drawable 不能证明内部渲染分辨率；单独扩大客体窗口仍可能让游戏
主动绘制装饰立柱。宽屏需从实际 viewport 计算定位共享虚拟宽度和默认视域，
严格校验原字节，只修改私有构建副本，不全局搜索替换所有 1920 常量。

必须看像素：同场景比较中央物体尺度，并确认两侧新增的是真实世界，
而非拉伸、裁剪或装饰背景。暂停菜单和字幕也要另测，原生 GUI 的绝对位置
不一定读取 Lua 的 `ScreenCenterX`。附着坐标不能重复平移，平台同名继承
也不一定是循环。

还有容易遗漏的状态来源：Hades 会保存和恢复 Lua 全局变量。
仅修改 UIData 的初始坐标，旧存档仍能把它覆盖回旧值。将显示专用坐标
列入现有 `SaveIgnores`，既能保留当前配置，也避免试验参数污染存档。
资源覆盖同时影响文件大小、目录大小、全读、部分读和 EOF；应先校验原资源，
不修改原文件或用新建存档掩盖兼容性问题。

**教训：窗口、世界、UI 和持久状态分别验证；本机正确不替代真机交付。**

固定画幅的后处理/暗角也是独立来源。把暗角对象按画布横向缩放只是候选，
大殿或武器庭院的成功呈现，不能证明塔尔塔罗斯的矩形暗区已消失；
需保存负面对照并在实际报告场景复现。

## 14. 圆形外观不等于圆形触摸区域

`cornerRadius` 只改变外观，默认 UIKit 命中仍是矩形。收紧菱形间距后，
应直接按圆形覆盖 `pointInside:withEvent:`，拒绝透明角落，才能避免相邻键抢占。
72 pt 圆形采用 56 pt 轴向步长时，相邻圆心约距 79.2 pt，圆不重叠，
即使矩形边界存在交叠。用实际安全区验证底边，并把组中心的下移量作为测试条件，
不要只检查常量变化或代码可以编译。纯几何测试也不替代真机多指操作和手感确认。

第 29 版的用户反馈进一步说明：`pointInside` 的纯几何回归与真实按压反馈不是
同一件事。其 Mac UIKit 命中检查也能通过，但用户仍报告字母附近才有效。
不能据此编造已经证实的 iOS 系统缺陷。第 30 版为四键独立处理命中和触摸生命周期，
明确绘制选中样式，并增加实际 UIKit 输入转发、渲染像素及多指状态回归；
测试替身仍不是物理触屏证据，需保留真机少量真实按下坐标作进一步核对。
第 30 版随后在完整备份、两次退出检查、覆盖安装与 10 份存档哈希一致后，
核对新启动收据，用户确认四键整圈触发及高亮正常。将这项物理操作确认
与本机回归分别记录，不把它扩展为宽屏遮罩已修复或所有触摸边界已实测。

第 31 版在用户批准后增加原生轻触反馈，绑定初始 `TouchDown` 而不是共用的
`controlDown:`，避免四键滑回时重复震动。普通界面按钮绑定确认激活，
不要在会被程序调用的日志刷新方法中触发。摇杆不绑定；复用轻量反馈生成器，
仅前台请求。UIKit 生成器替身可证明调用次数，不能证明设备实际震感；
